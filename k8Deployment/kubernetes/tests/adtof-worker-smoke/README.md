# ADTOF worker smoke fixture contract

## Reviewed live run (2026-09-27)

The fixed-coordinate ADTOF smoke passed after the worker's Helm adoption.
The versioned v002 test-only PostgreSQL functions recognize only the parent
finalizer's exact incomplete-stem result for this intentionally one-drum
four-stem fixture; an unrelated failure still preserves evidence. The pinned
Linux/ARM64 client image passed all 64 in-image tests. During the live run,
KEDA activated the Helm-owned worker from zero to one Pod. The client observed
real durable publication and first-attempt task success, independently verified
private MIDI and tempo bytes and provenance, then removed its three exact MinIO
objects and guarded database rows. The disposable Kubernetes smoke Job was
removed. The worker returns to zero after KEDA's 180-second idle cooldown.

The historical sections below describe how each narrow fixture boundary was
built. Use the [ADTOF release script](../../scripts/releases/adtof-release.rb) for a
new smoke run; inspect any failed fixed-coordinate attempt before cleanup.

This directory contains the deterministic input fixture, restricted database
and MinIO boundaries, pinned client image, and versioned Job for an **end-to-end
ADTOF worker smoke test**. The source files alone make no cluster change;
`adtof-release.rb smoke` runs the reviewed live test.

The deployed `clouddsp-adtof` worker is already the system under test. The
smoke client uses the existing generic dispatcher and worker rather than
publishing directly to RabbitMQ or simulating a worker result. With the ADTOF
KEDA ScaledObject applied, the same durable event is also the controlled
activation stimulus: the worker Deployment may be at zero replicas before the
test creates its request, and KEDA must create capacity from the real queue.

```text

        |

        |
        v
```

## Controlled drums WAV

`build_controlled_drum_fixture()` produces a valid four-second, 44.1 kHz,
mono, 16-bit PCM WAV entirely in memory. Its deterministic pattern contains a
120-BPM pulse: eight kick-like low transients, four snare-like high transients,
and sixteen short click transients. It is below one MiB, is not user media, and
uses no checked-in binary fixture or random generator.

The later client must calculate the generated byte length and lowercase
SHA-256 at run time, upload exactly the fixed `drums.wav` key, and provide the
same values to PostgreSQL. It must set exactly this Demucs-compatible MinIO
metadata inventory:

```text
schema-version=1    producer=demucs
job-id={fixed job}  task-id={fixed synthetic upstream task}
stem-name=drums     stem-mode=4-stems
size-bytes={size}   sha256={digest}
```

`producer=demucs` means the test object conforms to the output contract that
ADTOF independently verifies. It does not claim the fixture client ran Demucs.
The worker must still `HeadObject`, stream-download, and hash the WAV before
model execution.

## Expected worker result

The eventual observer must require that the generic dispatcher published the
fixed `adtof.requested` outbox event and that the deployed worker created one
`(job_id, adtof, drums)` task with attempt count one, cleared its lease, and
marked it `succeeded`. The parent Job is intentionally incomplete: it contains only the `drums`
part of a `4-stems` set. Migration v008 marks that synthetic parent `failed`
with its exact incomplete-stem error after the worker task succeeds. The
restricted observer returns `failed_incomplete_stem_fixture` only for that
combination; an unrelated failed parent remains `failed` and stops the test.

The observer must independently validate both stored MinIO objects. The MIDI
must be a non-empty valid Standard MIDI file with `audio/midi`; the tempo file
must be bounded valid JSON with `application/json`. Both need complete ADTOF
provenance/size/SHA-256 metadata matching the worker-created task ID, fixed
event, fixed input SHA-256, and pinned ADTOF configuration. The test does not
assert a musical note count, a particular BPM, or a high-confidence tempo: that
would turn a pipeline smoke test into a fragile model-quality benchmark.

## Failure and cleanup posture

The later smoke client must first refuse dirty fixed keys or durable rows. It
may clean up all three fixed objects and the one fixed Job/event only after it
has independently observed the full successful result. A failed or timed-out
run must preserve its evidence for diagnosis; a separate, scoped
administrator-only cleanup Job will be designed later. The smoke client will
have no RabbitMQ credentials: durable PostgreSQL publication, the generic
dispatcher, and the deployed ADTOF consumer form the behavior under test.

## Fixed-function PostgreSQL adapter (source only)

[`client/adtof_worker_smoke_database.py`](client/adtof_worker_smoke_database.py)
implements the second I/O-shaped boundary over an injected DB-API-like
connection factory. It imports no Psycopg and never constructs a connection.
Its three fixed SQL statements name only the administrator-owned
`prepare`/`observe`/successful-only `cleanup` functions—never application

`prepare` validates bounded fixture evidence and commits only the exact reserved
Job/event result. `observe` accepts only its compact eight-column projection
then rolls its read transaction back, so a later polling loop retains no idle

## KEDA activation use

This existing fixed-coordinate Job is the activation driver for the first
ADTOF KEDA observation. It deliberately has no RabbitMQ credential and does
not read Kubernetes resources: its limited PostgreSQL `prepare()` function
creates the one durable outbox event, the generic dispatcher publishes that
event, and KEDA observes the real `clouddsp.adtof.requests` backlog through
RabbitMQ's private management API. This keeps the test from forging a queue
message or granting its client authority to scale a Deployment.

Before an explicit activation run, confirm that the ADTOF ScaledObject is
`Ready`, its target Deployment is at `0/0`, the generic dispatcher is Ready,
and no prior fixed smoke evidence remains. While the Job is in its bounded
observation phase, inspect the generated HPA and ADTOF Pod count outside the
Job. A later focused observation task owns the exact commands and success
criteria for `0 -> 1`; this fixture Job still owns the eventual worker output
verification and successful-only cleanup.

This adapter is read-only: it cannot list a bucket, write an output, delete an
object, call PostgreSQL, publish RabbitMQ work, invoke ADTOF, build an image,
or create a Job.

## Successful-only fixed-object cleanup adapter (source only)

[`client/adtof_worker_smoke_minio_cleanup.py`](client/adtof_worker_smoke_minio_cleanup.py)
defines the smoke client's only destructive object-storage capability. It still
does not construct Boto3 or call another system. Before its first deletion it
requires all three independently established facts: a published, completed,
first-attempt, lease-cleared `failed_incomplete_stem_fixture` task observation; the fixed WAV
upload evidence; and the verified fixed MIDI/tempo output pair. Invalid or
incomplete evidence causes no S3 call.

The adapter deletes only the policy-granted `tempo`, `MIDI`, then input-WAV
keys. It does not accept a bucket, prefix, key, body, or retry setting. If an
S3 deletion fails, it stops immediately and reports one redacted infrastructure
error; it does not retry or speculate about the remaining evidence. The input
is deliberately last so a partial cleanup retains the reproducible test
stimulus for diagnosis.

There is no cross-service transaction between S3-compatible MinIO and
PostgreSQL. This module therefore does not claim object cleanup also removes a
Job/event.

## Orchestration state machine (source only)

[`client/adtof_worker_smoke_orchestration.py`](client/adtof_worker_smoke_orchestration.py)
is the pure workflow model that joins the existing small adapters without
calling them. Its sole legal action sequence is:

```text
preflight → upload input → durable prepare → bounded observation
          → output verification → object cleanup → guarded database cleanup → passed
```

The machine uses an injected future elapsed-time value rather than reading a
clock or sleeping. It treats not-yet-published/running work as progress until
the finite timeout, but treats a dead-letter, retry, second attempt, failed
task, or failed Job as a terminal failure that preserves evidence. A completed
first attempt permits output verification; only fully verified output permits
the explicit object-first/database-second cleanup sequence already expected by
the scoped PostgreSQL function.

The terminal report is deliberately truthful: failures before cleanup are
`failed_preserving_evidence` (or a timeout), while an S3 cleanup failure is
`object_cleanup_incomplete` and a database cleanup refusal/failure is
`database_cleanup_incomplete`. No state can silently retry, claim success, or
skip a prior safety boundary.

## Reviewed run procedure

Run these commands from the `CloudDSP` repository root. They intentionally use
the explicit `k3d-clouddsp-local` context, rather than relying on whichever
cluster happens to be your current `kubectl` context.

### 1. Read-only prerequisites

```bash
kubectl --context k3d-clouddsp-local get secret \
  --namespace clouddsp-app \
  clouddsp-adtof-worker-smoke-database-credentials \
  clouddsp-adtof-worker-smoke-minio-credentials

kubectl --context k3d-clouddsp-local rollout status \
  --namespace clouddsp-app \
  deployment/clouddsp-generic-dispatcher \
  --timeout=60s

kubectl --context k3d-clouddsp-local rollout status \
  --namespace clouddsp-app \
  deployment/clouddsp-adtof \
  --timeout=60s

kubectl --context k3d-clouddsp-local get job \
  --namespace clouddsp-app \
  adtof-worker-smoke
```

The first three commands confirm that the two restricted runtime identities and
the two deployed consumers exist; they do not display Secret values. The last
command is expected to report `NotFound` before a first run. If it instead
shows an existing Job, stop and inspect that run—do not delete or reapply it
automatically because its fixed evidence may still be valuable.

The earlier database/MinIO bootstrap Jobs are prerequisites too, but they have
a completion TTL and may no longer exist. Their lasting evidence is the two
app-namespace Secrets above plus their restricted PostgreSQL functions and
MinIO policy/user; do not recreate either bootstrap merely because its expired
Job object is absent.

### 2. Deliberately start one run

```bash
kubectl --context k3d-clouddsp-local apply \
  --filename k8Deployment/kubernetes/tests/adtof-worker-smoke/adtof-worker-smoke-job.yaml
```

This is the sole command in this procedure that creates a Kubernetes resource.
It creates one `adtof-worker-smoke` Job and its one Pod; the client then creates
the reserved fixed pipeline evidence through its restricted capabilities. Do
not use `--force`, `replace`, a generated Job name, or a second apply while the
Job exists.

### 3. Watch safe progress and final status

```bash
kubectl --context k3d-clouddsp-local logs --follow \
  --namespace clouddsp-app \
  job/adtof-worker-smoke

kubectl --context k3d-clouddsp-local get job,pod \
  --namespace clouddsp-app \
  --selector app.kubernetes.io/name=adtof-worker-smoke \
  --output wide

kubectl --context k3d-clouddsp-local describe job \
  --namespace clouddsp-app \
  adtof-worker-smoke
```

Expected safe milestones move from fixed-object preflight through upload,
durable event creation, dispatcher/worker observation, output verification, and
cleanup, ending with `ADTOF worker smoke: passed`. A non-zero Job is also a
useful result: preserve its logs and `describe` output. The Job deliberately
does not retry, and its failure/timeout leaves fixed database/object evidence
for a later, narrowly scoped cleanup task. Do not manually publish a RabbitMQ
message, edit the Job’s environment, or delete fixed objects to make a failure
appear successful.

The Job and Pod TTL-clean about ten minutes after either outcome, so inspect or
save safe diagnostics before then. The release script ran the equivalent procedure on 2026-09-27, observed a
passing result, and removed the disposable Job.
