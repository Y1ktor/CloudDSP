# Demucs worker smoke contract

This directory defines the bounded, production-like smoke test for the
already-deployed `clouddsp-demucs` worker.  The test does not publish an AMQP
message, simulate a worker result, call the Kubernetes API, or grant itself a
normal CloudDSP object's credentials.  Instead it follows the durable route
that a real source takes after upload intake has accepted it:

```text
controlled private WAV
        |
        v
fixed PostgreSQL prepare function creates source-uploaded Job + outbox event
        |
        v
generic dispatcher publishes demucs.requested
        |
        v
deployed Demucs worker claims, probes, separates, hashes, and uploads stems
        |
        v
PostgreSQL Demucs-task success + two durable downstream outbox events
```

The one-shot client has no RabbitMQ identity.  The deployed dispatcher remains
the only component that publishes work, and the deployed worker remains the
only component that consumes it.  This avoids a smoke test accidentally
passing by bypassing either responsibility.

## Fixed test coordinates

Each deliberate run uses these reserved identifiers.  They are never chosen by
a browser and the restricted database/MinIO policies hard-code them, so the
test cannot be redirected to another user's Job or object prefix.

| Evidence | Fixed value |
| --- | --- |
| Job ID | `12139966-5891-4d53-a817-f3ce1f264c61` |
| Demucs source event ID | `e20cf942-ef7b-478e-89c4-f4795ed801ec` |
| Owner marker | `clouddsp-demucs-worker-smoke` |
| Stem mode | `2-stems` |
| Private bucket | `clouddsp-uploads` |
| Source object | `uploads/12139966-5891-4d53-a817-f3ce1f264c61/demucs-worker-smoke.wav` |
| Expected stems | `stems/12139966-5891-4d53-a817-f3ce1f264c61/vocals.wav`, `stems/12139966-5891-4d53-a817-f3ce1f264c61/no_vocals.wav` |
| Cleanup-only MIDI keys | `midi/12139966-5891-4d53-a817-f3ce1f264c61/vocals.mid`, `midi/12139966-5891-4d53-a817-f3ce1f264c61/no_vocals.mid` |

The Demucs task ID and downstream event IDs are intentionally generated by the
real workers.  Fixing them would bypass the idempotent task-claim and
completion paths that this test is meant to observe.

## What a passing run proves

The smoke client first requires all five fixed object keys and its fixed
database coordinates to be absent.  It builds a deterministic two-second WAV,
computes its byte count and SHA-256, uploads only the source key with the same
`job-id` and `stem-mode` metadata that the normal upload contract requires,
and calls its narrow PostgreSQL `prepare(size, sha256)` capability.

That function atomically creates a `source_uploaded` two-stem Job and exactly
one `demucs.requested` outbox event.  The client polls a compact
security-definer `observe()` projection until it proves all of the following:

- the source event was publisher-confirmed as `published`;
- the deployed worker created one Demucs task, completed it on its first
  attempt, and cleared its lease;
- the Job reached `midi_processing` with exactly the two expected stem records;
- exactly two downstream Basic Pitch outbox events were inserted with the
  Demucs task/Job completion in the same durable transition; and
- both private stem objects have `audio/wav`, exact producer/job/task/stem
  metadata, a positive bounded length, and a metadata SHA-256 that matches a
  separately streamed read.

This is a Demucs-stage assertion.  The test does **not** judge the musical
quality of separation and does not validate Basic Pitch MIDI contents.  It
does wait for the two normal downstream Basic Pitch tasks to finish successfully
before cleanup.  That is a safety barrier only: deleting a stem while a real
downstream worker can still read it would create a false failure and leave a
race in the cluster.

## Credentials and cleanup

The client receives two deliberately independent, narrow identities:

- PostgreSQL can execute only three fixed `SECURITY DEFINER` functions:
  `prepare`, `observe`, and guarded `cleanup`.  It has no direct table,
  sequence, schema, DDL, role, or RabbitMQ authority.
- MinIO can upload/read/delete the one source, read/delete the two Demucs
  stems and the two cleanup-only MIDI keys, and cannot list a bucket, presign,
  write a stem/MIDI output, or access an ordinary CloudDSP prefix.

On a successful run, the client waits until no downstream Basic Pitch task is
active, removes only the five literal test keys, and calls guarded database
cleanup.  The database function refuses to delete unless the expected
first-attempt Demucs and downstream Basic Pitch states are durable.  Failed or
timed-out runs preserve rows and objects for diagnosis; they must be cleaned
through a separately reviewed, exact-coordinate recovery operation rather than
by rerunning the Job.

## Prerequisites and run order

Before applying the smoke Job, apply the two ignored Secret copies, then run
the PostgreSQL and MinIO bootstrap Jobs.  The bootstrap Jobs create the
restricted identities; they create no source object, smoke Job, RabbitMQ
message, or processing task.  The generic dispatcher, Demucs Deployment, and
Basic Pitch Deployment must already be healthy.

The prepared Job uses a digest-pinned client image and has no Service,
Ingress, ServiceAccount token, Kubernetes API access, AMQP credential, or ML
runtime.  Its bounded wait is deliberately shorter than the Kubernetes Job
deadline so Kubernetes can cleanly stop a stuck client.

## Reviewed apply and inspection procedure

These commands are intentionally **not** run by the image-build script.  The
two bootstrap Secrets are temporary administrator credentials and are deleted
as soon as the constrained smoke identities exist.  The two application
Secrets remain only for the one smoke Job.

```bash
# 1. Create the four locally ignored Secret resources.
kubectl --context k3d-clouddsp-local apply \
  --filename k8Deployment/.local/demucs-worker-smoke-database-credentials.secret.yaml \
  --filename k8Deployment/.local/demucs-worker-smoke-minio-credentials.secret.yaml \
  --filename k8Deployment/.local/demucs-worker-smoke-database-bootstrap-credentials.secret.yaml \
  --filename k8Deployment/.local/demucs-worker-smoke-minio-bootstrap-credentials.secret.yaml

# 2. Create the MinIO policy and the one-time identity bootstrap Jobs.
kubectl --context k3d-clouddsp-local apply \
  --filename k8Deployment/kubernetes/tests/demucs-worker-smoke/demucs-worker-smoke-minio-policy-v001-configmap.yaml \
  --filename k8Deployment/kubernetes/tests/demucs-worker-smoke/demucs-worker-smoke-database-bootstrap-job.yaml \
  --filename k8Deployment/kubernetes/tests/demucs-worker-smoke/minio-demucs-worker-smoke-objects-bootstrap-job.yaml

# 3. Require both bootstraps to finish successfully, then inspect their logs.
kubectl --context k3d-clouddsp-local wait --namespace clouddsp-data \
  --for=condition=complete job/demucs-worker-smoke-database-bootstrap --timeout=3m
kubectl --context k3d-clouddsp-local logs --namespace clouddsp-data \
  job/demucs-worker-smoke-database-bootstrap
kubectl --context k3d-clouddsp-local wait --namespace clouddsp-data \
  --for=condition=complete job/minio-demucs-worker-smoke-objects-bootstrap --timeout=3m
kubectl --context k3d-clouddsp-local logs --namespace clouddsp-data \
  job/minio-demucs-worker-smoke-objects-bootstrap

# 4. Remove the temporary administrator Secrets before starting the client.
kubectl --context k3d-clouddsp-local delete \
  --filename k8Deployment/.local/demucs-worker-smoke-database-bootstrap-credentials.secret.yaml \
  --filename k8Deployment/.local/demucs-worker-smoke-minio-bootstrap-credentials.secret.yaml

# 5. Start the end-to-end smoke Job itself.
kubectl --context k3d-clouddsp-local apply \
  --filename k8Deployment/kubernetes/tests/demucs-worker-smoke/demucs-worker-smoke-job.yaml

# 6. In one terminal watch its Pod; in another stream the authoritative log.
kubectl --context k3d-clouddsp-local get jobs,pods --namespace clouddsp-app \
  --selector app.kubernetes.io/name=demucs-worker-smoke --watch
kubectl --context k3d-clouddsp-local logs --follow --namespace clouddsp-app \
  job/demucs-worker-smoke

# Optional: view final conditions and Kubernetes events after it exits.
kubectl --context k3d-clouddsp-local describe job --namespace clouddsp-app \
  demucs-worker-smoke
```

The smoke Job self-cleans only after proving the Demucs success state and
waiting for the two downstream Basic Pitch tasks to finish.  If it fails or
times out, it preserves its five literal objects and fixed database rows for
review instead of hiding the evidence.

### Diagnosed failed-run cleanup

The later inspected failure left one `source_uploaded` fixed smoke Job, its
one published Demucs outbox event, and one inactive first-attempt
`retry_scheduled` Demucs task with `demucs_process_failed`. The Demucs queue
and its DLQ were empty, so a queue purge would be both unnecessary and unsafe.
[`demucs-worker-smoke-failed-run-cleanup-job.yaml`](demucs-worker-smoke-failed-run-cleanup-job.yaml)
is the reviewed recovery path for exactly this state. Its first init container
deletes only that task when every fixed event/source/status/attempt/error and
no-lease guard still matches, then deletes only the fixed Job and its matching
sole outbox event. This ordering prevents a worker-recovery race while object
cleanup runs. Its second init container deletes only the five literal object
keys. If a first run completed the database phase but MinIO was unavailable,
the all-absent database shape is an idempotent retry for those same literal
keys only. The Job has no RabbitMQ authority, cannot list an object prefix, and
cannot delete a normal CloudDSP Job.

```bash
kubectl --context k3d-clouddsp-local apply \
  --filename k8Deployment/kubernetes/tests/demucs-worker-smoke/demucs-worker-smoke-failed-run-cleanup-job.yaml

kubectl --context k3d-clouddsp-local wait --namespace clouddsp-data \
  --for=condition=complete job/demucs-worker-smoke-failed-run-cleanup --timeout=3m

kubectl --context k3d-clouddsp-local logs --namespace clouddsp-data \
  job/demucs-worker-smoke-failed-run-cleanup --all-containers
```
