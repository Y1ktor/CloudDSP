The first post-adoption run exposed an obsolete parent-status assertion. The

but migration v008 correctly failed the deliberately incomplete two-stem

removed only its two MinIO objects and matching PostgreSQL Job/event/task.

The restricted `observe` and `cleanup` functions now recognize only that exact
fixture finalization error. A versioned v002 ConfigMap and one-shot Job installed
those functions; the original bootstrap source contains the same definitions
for a fresh cluster. The rebuilt Linux/ARM64 client image passed all nine
in-image tests and is digest-pinned in the smoke Job and image lock.

The rerun passed: the event was published, the worker task succeeded on its

provenance, and successful cleanup removed the fixed MinIO keys and database
rows. The disposable Kubernetes smoke Job was removed. The separate

## What one successful run proves

The smoke test must exercise the production-like durable path below.  It must
use the already deployed generic dispatcher and Basic Pitch worker; it must not
simulate either component or publish a message directly to RabbitMQ.

```text
controlled WAV in private MinIO
        |
        v
test-specific PostgreSQL prepare function creates Job/outbox event
        |
        v
generic dispatcher publishes basic-pitch.requested
        |
        v
deployed Basic Pitch worker claims, verifies, downloads, runs, and uploads
        |
        v
PostgreSQL task is succeeded and private MIDI object is present
```

This proves the hand-off from a durable downstream event, through RabbitMQ,
into the actual CPU worker and back into the authoritative database and object
store.  It does **not** prove browser upload, Keycloak/OIDC, Demucs separation,
ADTOF, Job-level MIDI aggregation, KEDA scale-out, or frontend display. Those
remain separate smoke tests.

## Fixed, reserved test coordinates

Every run uses these canonical UUIDs and object keys.  They are reserved only
for this test, never for a browser-created Job.  Fixed coordinates make the
later MinIO policy exact: the smoke identity can be limited to two objects
instead of receiving access to every stem or MIDI result.

| Evidence | Fixed value |
| --- | --- |
| Job ID | `7ea5ee7e-c726-4af8-8f21-4d0e227bdd0b` |
| Synthetic Demucs stem task ID | `3ed3ddfa-3165-4365-af60-5ae4f7f656ba` |
| Basic Pitch request-event ID | `66d8637f-4e80-4b53-aed3-4e4ea54bd110` |
| Stage | `basic-pitch` |
| Stem mode | `2-stems` |
| Stem name | `vocals` |
| Private bucket | `clouddsp-uploads` |
| Controlled input object | `stems/7ea5ee7e-c726-4af8-8f21-4d0e227bdd0b/vocals.wav` |
| Expected MIDI object | `midi/7ea5ee7e-c726-4af8-8f21-4d0e227bdd0b/vocals.mid` |

`vocals` is deliberately used because it is valid for `2-stems` and is an
allowed Basic Pitch stem.  The test must reject a run when any fixed row or
object is already present: a previous failed run must be investigated or
cleaned before another run can claim the same identity.

The actual Basic Pitch `processing_tasks.task_id` is intentionally **not**
fixed. The deployed worker creates it only after it has consumed and
durably claimed the request, which is the same idempotent path used for normal
work. The fixed synthetic task ID above is instead the upstream Demucs-task
provenance attached to the synthetic WAV. The smoke observer records the
worker-created Basic Pitch task ID and requires the resulting MIDI metadata to
match it.

## Controlled source object

The later smoke client will generate a small deterministic PCM WAV in memory
(a one-second, 440 Hz mono tone), calculate its byte length and lower-case
SHA-256, and upload it **before** it asks PostgreSQL to create an event.  A
real Demucs output is not required for this test, but the synthetic object must
faithfully satisfy the contract Basic Pitch independently enforces for a
Demucs-produced stem:

- bucket/key exactly match the fixed input coordinate above;
- `Content-Type` is exactly `audio/wav`;
- object size and SHA-256 exactly match the generated bytes; and
- the complete S3 user-metadata set contains only these keys:
  `schema-version=1`, `producer=demucs`, fixed `job-id`, fixed `task-id`,
  `stem-name=vocals`, `stem-mode=2-stems`, `size-bytes`, and `sha256`.

The `producer=demucs` value here means “matches the Demucs output contract”; it
does not claim that the smoke client ran Demucs.  Basic Pitch verifies this
metadata before it downloads a byte, then streams and hashes the WAV again.
This is important: an event can never make the worker see an absent source
object or a source whose durable evidence disagrees with storage.

## Durable test boundary

The applied test database login has no direct table, sequence, schema, or DDL
authority. It receives only three `SECURITY DEFINER` functions scoped to the
fixed coordinates:

1. **prepare** verifies the caller supplies the fixed IDs and exact input
   byte/hash evidence, then atomically creates the eligible `midi_processing`
   Job and one `basic-pitch.requested` downstream outbox event. The deployed
   worker later creates its own first Basic Pitch `vocals` task while claiming
   that published event.
2. **observe** returns a compact projection of only this Job/event/task: outbox
   publication state, task status/attempt/lease/completion fields, and the
   exact expected parent-finalization marker. It must not expose other users' Jobs, source
   objects, credentials, or arbitrary table contents.
3. **cleanup** deletes only these fixed test rows and only after successful
   observation of the expected completed task.  It must never be a general
   deletion capability.

The parent Job is deliberately incomplete: it contains only `vocals` of a
`2-stems` set. After the real Basic Pitch task succeeds, migration v008 marks
that synthetic parent `failed` with its exact incomplete-stem error. The
restricted `observe` function maps only that combination to
`failed_incomplete_stem_fixture`; any unrelated parent failure remains
`failed` and causes the client to stop without cleanup.

The applied MinIO policy gives the smoke client only `PutObject`,
`GetObject` (which also authorizes `HeadObject`), and `DeleteObject` for the
two fixed keys. It must not list a bucket, issue presigned URLs, access
`uploads/*`, or access any normal `stems/*` or `midi/*` prefix. No smoke
RabbitMQ identity is needed: the generic dispatcher publishes and the deployed
worker consumes using their own restricted production identities. Consequently
the smoke test cannot steal a delivery, alter queue topology, or bypass durable
publication.

## Required ordering and evidence

The one-shot Job performs the following order exactly:

1. Preflight that its fixed database rows and both fixed MinIO keys are absent.
2. Generate, hash, and upload the controlled WAV with the complete Demucs
   metadata contract.
3. Call `prepare`; this is the first time a durable Basic Pitch request can
   exist.
4. Poll `observe` until the generic dispatcher has recorded the event as
   published and the deployed worker records the one Basic Pitch task as
   `succeeded`.
5. Independently `HeadObject` and stream-read the expected MIDI object.  It
   must have `audio/midi`, a non-zero length, a SHA-256 metadata value matching
   the streamed body hash, and a valid Standard MIDI File header.  Its complete
   Basic Pitch provenance metadata must match the fixed Job/task/event/stem and
   the synthetic input SHA-256.
6. Delete only the two fixed MinIO objects, then call scoped database cleanup.
   Deleting storage first preserves the durable database evidence if object
   cleanup fails.

The test must log compact milestone names and safe IDs/statuses only.  It must
not print credentials, presigned forms, access tokens, raw RabbitMQ messages,
audio, or MIDI bytes.

## Failure, timeout, and cleanup policy

- The client wait is bounded to 180 seconds. The Kubernetes Job uses a
  300-second `activeDeadlineSeconds` and `backoffLimit: 0`.  Basic Pitch model
  startup can take longer than the tiny input warrants; the deadline detects a
  broken worker rather than hiding it with retries.
- Before `prepare`, the client removes only a just-created controlled input if
  its own upload step fails.  It must not touch any other coordinates.
- Once `prepare` succeeds, a failed or timed-out run preserves its fixed
  database rows and objects for diagnosis.  It must not automatically erase
  evidence of a dispatcher, worker, or storage failure.
- Only a fully successful observation permits automatic scoped cleanup.  A
  documented manual-cleanup command may remove exactly the same fixed
  resources after a human has inspected a failed run.

### Diagnosed failed-run cleanup

[`basic-pitch-worker-smoke-failed-run-cleanup-job.yaml`](basic-pitch-worker-smoke-failed-run-cleanup-job.yaml)
is the one explicit administrator-only recovery path after that inspection. It
first removes only the fixed `stems/{job_id}/vocals.wav` and
`midi/{job_id}/vocals.mid` smoke keys, then deletes exactly one *expired*,
`failed` smoke Job with the exact incomplete-stem error, fixed owner/event
coordinates, and one succeeded first-attempt Basic Pitch task. PostgreSQL
cascades only that Job's matching event and task. It has no
RabbitMQ credential and intentionally preserves the prior dead-letter message.
It fails on a missing or mismatched database row rather than becoming a general
cleanup mechanism. A new smoke Job may be started only after its logs confirm
this deliberate cleanup completed.

## Why this is not the existing routing smoke

`tests/generic-dispatcher-smoke/` proves a narrower property: a synthetic
outbox event reaches `clouddsp.basic-pitch.requests`.  Its reader would race
the deployed Basic Pitch worker for that delivery, and its synthetic event has
no valid private WAV to process.  Running it alongside the real worker could
either hide a consumer problem or deliberately create a terminal worker
failure.  This worker smoke observes durable database and MinIO evidence
instead, so it never competes for a queue message.

After the [Basic Pitch Flux handoff](../../gitops/basic-pitch.md), the same
release runner verifies Flux and native ownership before creating the versioned
smoke Job. No chart or policy override is needed for this processing smoke.
The client follows the existing dispatcher/worker path and uses restricted
PostgreSQL and MinIO identities, with no RabbitMQ or Kubernetes API access.
Wait for KEDA cooldown and worker Pod termination before `verify-idle`.

Credentials may be generated in memory and submitted directly to Kubernetes
from the public Secret examples. Keep the four Secret copies absent before
creating temporary access; never print their values or commit local credentials.
Inspect successful database/MinIO bootstrap Jobs, then remove those exact Jobs
and their two `clouddsp-data` temporary credential Secrets. The two client
Secrets in `clouddsp-app` remain until the smoke succeeds.

For test identities provisioned solely for a successful trial, create the
bounded [retirement Jobs](basic-pitch-worker-smoke-retire-jobs.yaml):

```sh
kubectl --context k3d-clouddsp-local create -f \
  k8Deployment/kubernetes/tests/basic-pitch-worker-smoke/basic-pitch-worker-smoke-retire-jobs.yaml
```

Inspect both completions and logs before removing those exact Jobs, the two
client Secrets, and `clouddsp-basic-pitch-worker-smoke-objects-policy-v001`.
Database retirement refuses remaining reserved evidence and drops only the
three test functions and role. MinIO retirement requires both reserved prefixes
to be empty before removing the test user/policy; it deletes no objects. Failed
or interrupted runs retain their evidence and require diagnosis before cleanup,
retirement, or a rerun.
